# Seeker consultation routing milestones

One shared seeker hospital account; no additional staff accounts. Providers use their own phone and do not register callback devices. Stop for review after each milestone.

- [x] **1. Seeker installation registration.** Save staff name, device name, and contact number against a persistent app installation. Prompt each new seeker installation even if the shared account already has other devices. Providers are not prompted. Development schema applied without truncating unrelated data. Mobile typecheck and API startup checked; no Expo export or device build requested.
- [x] **2. Booking assignment and shift handoff.** Seekers choose an eligible registered staff/device pair for each consultation and can change only that booking's pair as shifts change, including to another staff installation. The server validates ownership, staff name, and linked installation; mobile and web show the selected pair. Mobile typecheck passed. The web typecheck still has pre-existing errors in unrelated files; no end-to-end device test was run.
- [x] **3. Targeted in-app ringing.** Provider-to-seeker calls use the booking's selected installation for native push, browser push, foreground polling, live events, and answer/decline; missing or unlinked targets fail closed rather than ringing the shared account. Seeker-to-provider calls retain their existing delivery. The two additive columns were applied to the development database. Focused native-push tests and API startup/health checks passed; no Expo build or real-device call test was run.
- [x] **4. Twilio voice reminder and combined path checks.** The selected booking contact receives an at-most-once Twilio voice reminder in the ten minutes before the appointment, never the shared account or ward phone. A handoff within that window may remind the newly selected contact. The old start-time seeker call was removed; provider/admin start-time calls remain unchanged. Focused checks cover the seeker reminder, handoff, missing device, provider-to-seeker targeting, and seeker-to-provider delivery; API startup and health checks passed. No real Twilio call or two-device end-to-end test was run.

Milestones 1–4 are implemented in development. Actual Twilio delivery and the selected-installation call path have not been verified with real phones/devices. An uncertain Twilio outcome is logged but not automatically redialed, to avoid duplicate calls after a crash.
