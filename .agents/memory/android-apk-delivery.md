---
name: Android APK delivery
description: Provenance of previous installable builds and how to avoid misidentifying their source
---

Previous installable Android APKs for this project were generated through Expo's cloud build service using an Expo credential supplied in the workspace, not through a GitHub-connected build. The user explicitly confirmed this after being incorrectly directed to GitHub. Current Replit Expo guidance does not provide a native Android APK publishing route; do not treat the historical route, an existing EAS profile, or a configured credential as authorization to use EAS CLI or imply that a Replit build has started. The connected Expo integration can read historical builds even when its build-start route cannot run: that route separately requires a GitHub repository linked to the Expo project.

**Why:** The Expo builds dashboard displays a "Build from GitHub" action regardless of how earlier builds were started. Mistaking that button for proof of GitHub synchronization sent the user toward a stale build path. A configured EAS profile or working Expo credential does not prove the build-start route has a usable source repository.

**How to apply:** For any new APK request, check current Replit Expo capabilities first and distinguish API/web builds from native APKs. Verify the actual build source and commit before telling the user to install a file; never claim a fresh APK exists until a supported build completes. If a build-start route needs a repository, confirm the Expo project is linked to one and the intended revision is available there. A previous build can be offered only as a clearly labeled existing build after checking whether mobile code changed; never silently replace a requested fresh build with it or sync source to an external repository without consent.
