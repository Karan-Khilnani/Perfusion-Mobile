## TASK: Fix Consultation Status / Pause / Resume Functionality

The current consultation status functionality has the following problems:

### 1. Default Consultation Status

Current problem:

* A consultation is currently appearing as "Paused" by default.

Required behavior:

* A newly active consultation must be **Open/Active by default**.
* It should NOT automatically start in Paused state.
* The consultation should become Paused only when the Provider explicitly pauses it.
* The Provider must be able to resume the consultation through the same status control.

### 2. Provider Status Control

Required behavior:

* The Provider should be able to interact with the consultation status control.
* The status should support at least:

  * Open/Ongoing
  * Paused
* When the Provider pauses the consultation, its state must change to Paused.
* When the Provider resumes it, its state must change back to Open/Ongoing.

### 3. Status and Pause/Resume Must Be One Integrated Flow

Do not implement separate unrelated controls for:

* consultation status
* pause
* resume

The status control should represent the actual consultation state.

Expected behavior:

OPEN/ONGOING
→ Provider taps status
→ PAUSED

PAUSED
→ Provider taps status
→ OPEN/ONGOING

The UI must always reflect the actual underlying state.

### 4. Persistence / Data Consistency

Before implementing anything, inspect how consultation status is currently stored.

Determine:

* Where the consultation status originates.
* Whether it is stored locally, remotely, or both.
* Which API/database field represents the status.
* How the status is retrieved when opening/reloading a Case File.
* How the Provider Dashboard gets the status.

Then implement the fix using the existing architecture.

IMPORTANT:

* Do not create a new status field if an existing field already represents this state.
* Do not maintain two competing sources of truth.
* If the status is persisted remotely, make sure the mobile UI updates the actual persisted state.
* If the app currently uses optimistic UI, handle API failure so the UI does not falsely show a state that was not successfully saved.
* Handle loading and error states appropriately.

### 5. Case File / Consultation Consistency

The status shown in the relevant Provider screens must represent the same consultation state.

Verify that:

* Opening a consultation shows the correct state.
* Pausing updates the state.
* Resuming updates the state.
* Leaving and reopening the consultation does not incorrectly reset it.
* Refreshing/reloading does not incorrectly turn a paused consultation into Open or an Open consultation into Paused.
* Dashboard and Case File do not show conflicting states.

### 6. Chat Window

The same consultation-status principle should apply to the Chat window.

Inspect the existing Chat implementation and determine how it currently relates to the consultation state.

The goal is:

* Chat should reflect the actual consultation state.
* Pause/resume should not create a separate contradictory state.
* Do not create a second independent consultation-status system for Chat.

Only make changes necessary to correctly synchronize the existing consultation state.
