DO NOT modify:

There is currently NO Forgot Password option.

We need to add a complete Forgot Password / account recovery flow.

==================================================
1. ADD "FORGOT PASSWORD?" TO SIGN IN SCREEN
==================================================

Add a clearly visible:

"Forgot Password?"

option underneath the Password field and above the Sign In button.

It should be tappable.

Do not remove or change:
- Sign in with Google
- Email field
- Password field
- Sign In button
- Create a new account

Keep the existing Perfusion visual style.

==================================================
2. FORGOT PASSWORD SCREEN
==================================================

When the user taps "Forgot Password?":

Navigate to a dedicated Forgot Password screen.

The screen should contain:

Title:
"Forgot Password?"

Supporting text explaining that the user can enter their registered email address to receive a verification code/link.

Email input:
- User enters their email address.

Button:
"Continue" or an equivalent clear action.

Include appropriate validation for:
- Empty email
- Invalid email format

Do not proceed with an invalid email address.

==================================================
3. CHECK WHETHER EMAIL IS REGISTERED
==================================================

When the user submits the email:

The system must determine whether the email is registered with a Perfusion account.

IMPORTANT:
Do NOT simply assume every email is registered.

There are two possible paths.

PATH A — REGISTERED EMAIL

If the email belongs to an existing Perfusion account:

- Send the configured verification email to that address.
- The email should contain the verification mechanism already supported/configured by the application.
- This may be a verification code or verification link depending on the existing authentication/backend implementation.
- Do not create a new authentication mechanism if one already exists.
- Reuse the existing configured email/OTP infrastructure where possible.

Then navigate to the verification screen.

PATH B — EMAIL NOT REGISTERED

If the email does NOT belong to a registered Perfusion account:

Show a clear message such as:

"This email is not registered."

Provide an action:

"Create an account"

When the user taps it:
- Navigate to the existing Create Account/Sign Up flow.
- Do not create a second registration flow.

Do not send a password-reset email to an unregistered address.

==================================================
4. VERIFICATION SCREEN
==================================================

For a registered email, show a verification screen.

Display the email address being verified.

Provide an input for the verification code.

Example:

"Enter verification code"

[ _ _ _ _ _ _ ]

The exact number of digits must match the existing backend/email verification implementation.

Provide:
- Verify button
- Resend code option if supported by the existing authentication system
- Appropriate loading state
- Appropriate invalid/expired code error

The user must not be authenticated until the verification is successfully completed.

If the verification code is incorrect:
- Do not sign the user in.
- Show an appropriate error.
- Allow them to try again.

If the verification code is expired:
- Clearly indicate that it expired.
- Allow the user to request/resend a new code if the backend supports it.

==================================================
5. SUCCESSFUL VERIFICATION
==================================================

After the verification code is successfully validated:

The user should be authenticated into their existing Perfusion account.

IMPORTANT:

The user should NOT be forced to change their password.

Password change is OPTIONAL.

After successful verification, show a screen/step such as:

"Verification successful"

Then provide:

"Change Password"

and

"Continue to Dashboard"

The user must be able to skip the password change.

==================================================
6. OPTIONAL PASSWORD CHANGE
==================================================

If the user chooses "Change Password":

Show:

New Password
Confirm New Password

Validate:
- Password is not empty.
- Password meets the existing application's password requirements.
- Confirm Password matches New Password.

Then provide:

"Update Password"

After a successful password update:
- Confirm that the password was changed.
- Continue to the Dashboard.

IMPORTANT:
Changing the password is OPTIONAL.

The user must be able to skip this step and continue to the Dashboard without changing the password.

==================================================
7. CONTINUE WITHOUT CHANGING PASSWORD
==================================================

If the user chooses:

"Continue to Dashboard"

without changing their password:

- Do NOT force a password update.
- Do NOT show the password-change screen again.
- Keep the authenticated session.
- Navigate to the appropriate existing Provider/Seeker Dashboard based on the user's actual account role.

Do not create a temporary fake session.

The authentication session must be real and persistent according to the existing authentication system.

==================================================
8. AUTHENTICATION / SECURITY
==================================================

Before implementing anything, inspect the existing authentication architecture.

Determine:
- Which authentication provider/backend is currently being used.
- How email/password accounts are stored.
- How sessions/tokens are created.
- Whether OTP/email verification already exists.
- Whether a password reset mechanism already exists.
- Whether Google authentication uses the same user/session system.
- How Provider vs Seeker roles are determined.

Reuse the existing authentication infrastructure wherever possible.

DO NOT:
- Store verification codes in the mobile app.
- Hardcode verification codes.
- Store passwords in local storage.
- Create a fake local authentication state.
- Automatically authenticate an unverified user.
- Expose whether an account exists through insecure client-side logic if the backend has a secure account-recovery mechanism.

If the backend already has password-reset or email-verification APIs, use those APIs rather than creating duplicate endpoints.

If backend changes are absolutely required, make only the smallest changes necessary for this recovery flow.
