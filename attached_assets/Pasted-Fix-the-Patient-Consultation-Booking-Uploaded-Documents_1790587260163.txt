Fix the Patient Consultation Booking → Uploaded Documents → Provider Case File Chat attachment flow in BOTH WEB and MOBILE where applicable.

IMPORTANT:
This is a bug fix for patient documents/files uploaded during consultation booking.

The required behavior is:

SEEKER BOOKING FORM
        ↓
Patient documents uploaded
        ↓
Consultation booked successfully
        ↓
Documents remain permanently associated with that consultation/booking
        ↓
Provider opens the Case File
        ↓
Uploaded documents are immediately visible in the Case File Chat
        ↓
Provider can preview/open the documents
        ↓
Provider can download the original files

Do NOT modify unrelated consultation, chat, authentication, calling, booking, or Case File functionality.

==================================================
1. CURRENT BUG
==================================================

Currently:

1. Seeker/Hospital opens the Consultation Booking Form.
2. Patient documents/reports are uploaded.
3. Consultation is booked successfully.
4. Provider opens the corresponding Case File.
5. The uploaded documents are NOT visible in the Case File Chat.

This means the uploaded files are either:

- not being persisted correctly,
- not being associated with the booking/consultation,
- not being returned by the Case File API,
- not being converted into Chat attachments/messages,
- or not being rendered by the Provider Mobile/Web Case File Chat.

Find the actual root cause.

Do NOT simply hide/show UI elements to make the problem appear fixed.

==================================================
2. REQUIRED FINAL BEHAVIOR
==================================================

When the Seeker uploads patient documents during consultation booking and successfully books the consultation:

The uploaded documents must become associated with THAT exact consultation/case.

When the Provider opens the corresponding Case File:

The documents must already be visible in the Case File Chat.

The Provider should NOT need to:

- refresh repeatedly,
- re-upload the documents,
- manually search for them somewhere else,
- reopen the booking form,
- wait for another unrelated action.

The documents should appear immediately after the consultation has been successfully booked and the Provider opens the Case File.

5. FILES MUST BE ASSOCIATED WITH THE CORRECT CONSULTATION
==================================================

This is critical.

If Patient A books Consultation A and uploads:

- ECG.pdf
- Blood_Report.pdf
- Prescription.jpg

those files must be associated with Consultation A.

They must NOT:

- appear in another patient's Case File,
- appear in another consultation,
- be associated only with the patient without consultation context if the existing architecture requires consultation-level association,
- disappear after booking.

Use the existing booking/consultation identifiers and relationship structure.

Do not rely only on filename matching or patient name matching.

==================================================
6. UPLOAD BEFORE BOOKING
==================================================

The booking flow may upload files before the consultation is finally created.

Handle this correctly.

If files are uploaded before the booking ID/consultation ID exists:

1. Temporarily retain the uploaded file metadata/reference.
2. Successfully create the consultation.
3. Associate the uploaded files with the newly created consultation.
4. Create the appropriate Case File Chat attachment/message records if required by the existing architecture.
5. Make them available to the Provider.

Do not lose uploaded files simply because the consultation ID did not exist at the moment of file selection.

==================================================
7. BOOKING FAILURE
==================================================

Handle unsuccessful bookings correctly.

If the consultation booking fails:

Do not create a fake Case File Chat message.

Do not associate documents with a non-existent consultation.

Existing upload cleanup/orphan-file behavior should be preserved or improved where necessary.

Do not delete a file that is still required by a successfully created booking.

==================================================
8. CREATE CASE FILE CHAT ATTACHMENT
==================================================

After the consultation is successfully booked, the uploaded patient documents should be available in the corresponding Case File Chat.

If the existing Chat architecture represents attachments as Chat messages, create the appropriate attachment/message records using the existing mechanism.

For example:

Consultation A
    ↓
Chat
    ↓
Attachment message
    ↓
ECG.pdf

The attachment should appear as a normal file attachment in the Case File Chat.

Do NOT create a fake text message such as:

"File uploaded"

without actually attaching the file.

==================================================
9. IMMEDIATE VISIBILITY
==================================================

When the Provider opens the Case File after booking:

The uploaded documents should already be present in the Chat.

The Provider should not have to manually trigger synchronization.

If the Case File Chat is already open when the booking/attachment becomes available:

Use the existing chat refresh/realtime mechanism where available.

Do not add unnecessary polling if the existing architecture already supports realtime updates.

If realtime is not currently implemented for this flow, make sure the attachment is returned immediately when the Case File Chat is fetched/opened.

11. DOWNLOAD
==================================================

The Provider must be able to download the original uploaded document where supported.

The downloaded file must be the original file uploaded by the Seeker/Hospital.

Do not generate a placeholder.

Do not change the file contents.

Use the existing authenticated/signed file-access mechanism.

12. SECURITY / PATIENT DATA
==================================================

These are patient documents and may contain sensitive healthcare information.

Do NOT make the uploaded files publicly accessible just to make previewing work.

Maintain existing authorization.

Only authorized users participating in the corresponding consultation should be able to access the documents.

Do not expose:

- Storage credentials
- Private bucket credentials
- Signing secrets
- Authentication tokens

in client-side code.

==================================================
19. ERROR HANDLING
==================================================

Handle these cases correctly:

A. File upload succeeds + booking succeeds
→ Document appears in Case File Chat.

B. File upload fails
→ Booking should handle the failure according to existing product behavior.
→ Do not create a broken attachment.

C. Booking fails after upload
→ Do not associate the file with a fake consultation.

D. File metadata exists but storage file is missing
→ Show an appropriate unavailable/error state rather than crashing.

E. Provider cannot access the file
→ Return appropriate authorization/access error.

F. Multiple files uploaded
→ ALL successfully uploaded documents should appear.
